Architecture, in essay form.

Picture a single abnormal sensor reading travelling from left to right across a diagram. Everything to the left of the gate in the middle is a proposal, and nothing to the right of that gate happens without a person. In the drawing, the colour of a box tells you who is responsible for it: blue is deterministic code, violet is the trained model, amber is the language model, and green is human authority. Telemetry is detected by deterministic code, classified by physics rules together with a narrow trained model, explained by a language model, and then approved by a named human before any work order exists in the maintenance system at all.

Who decides what.

The diagram is really a single statement about ownership. Each decision has exactly one owner, and no owner can quietly take over another's job.

The question of whether a reading is abnormal belongs to deterministic code, and it lives in backend app detector py. The question of what kind of fault it is belongs to physics rules first, with a narrow trained model brought in only for the one overlapping pair the rules cannot separate; that logic lives in backend app classifier py and backend app ml classifier py. The question of whether the evidence is strong enough to answer at all belongs to calibration, which is judged against precedent and signature agreement in backend app agent calibration py.

The question of how a fault is explained, and what work should be proposed, belongs to the language model, whether that is the mock policy or a live provider, both speak the same tool protocol, and it lives in backend app agent triage py and backend app agent L L M py. The question of how urgent the fault is belongs to a published formula in backend app priority py; the agent is allowed to move the result one notch, with a written reason, and can never downgrade a P1.

The question of whether any work actually happens belongs to a named human, expressed as a POST to cases id decision in backend app routes py. And the question of where approved work lands belongs to the CMMS, reached over HTTP and idempotently, through backend app agent C M M S adapter py and backend app C M M S service py.

What runs where.

The runtime picture is a Next.js frontend on Vercel talking to a FastAPI backend on Render. The backend holds the ingest, detection, classification, agent, and decision modules, plus a mounted CMMS service. Behind it sit a Supabase Postgres database and a capped, off-by-default OpenRouter model.

Why the boundaries sit where they do.

Detection is deterministic. It combines fixed engineering limits with a robust rolling median and median-absolute-deviation excursion that has to persist before it counts. A technician can read the rule that fired, and the same reading always produces the same result.

The trained model is deliberately narrow. It has exactly one job: separating suction restriction from discharge restriction on the SKAB pump, which is the pair that physics rules cannot cleanly split. An IsolationForest novelty score and an exact feature-roster check make it abstain on anything outside that job, rather than answering confidently in a domain it was never trained on.

The language model never decides. It retrieves precedent, explains the evidence, and drafts the work order. Fault class, priority, and the existence of a work order are all owned elsewhere, so a fluent wrong answer costs an explanation rather than a maintenance action.

Confidence is grounded rather than self-reported. A model's own certainty tracks its fluency, not its correctness, so the calibrated number here is built instead from matching precedent and signature agreement. Below a calibrated confidence of 0.45 the case is flagged as one the system will not answer, and it still reaches a planner, marked as uncertain.

The human gate is structural. A work order is created in one place, after one state transition, by a request that carries both a bearer token and a reviewer name. There is no autonomous path from telemetry to action, by construction.

The CMMS is a separate service rather than a function call. The triage backend reaches it over HTTP with an idempotency key and a retry, exactly as it would reach SAP or Maximo. Repointing the C M M S BASE U R L setting swaps the system of record without touching anything above that line.

Spending is opt-in. Mock mode is the deployed default even when an API key is present, on the principle that a credential is not permission to spend. Live mode is capped at twelve provider calls and twenty-five cents per day, with 700 output tokens per call. Every call is costed into the L L M calls table, and hitting a cap or a provider failure drops the case back to the free deterministic policy and records that fact in the case trace.

What these diagrams do not claim.

Eight real replay episodes across two laboratory testbeds do not establish production accuracy, and the CWRU sequences in particular are constructed from real steady-state recordings rather than natural fault onsets. The trained layer is complete only for the restriction pair it was built for. And the boxes in the diagrams describe the code in this repository, so deployment-affecting changes are live only once they have been pushed and redeployed.

The measured numbers themselves live in the evaluation guide and the current status essay. The line-by-line walkthrough lives in the code and data-flow reference.

The diagrams themselves.

Both diagrams are plain SVG in the diagrams folder, readable text, edited in place, with no build step and no external assets.

There is also an interactive version, diagrams architecture interactive html, which is the same content as a single self-contained page you step through. It covers four flows: fault triage, the human decision, an abstention, and live model spend. It shows the payload at each step, and offers a mock-versus-live toggle and a dark-or-light theme. You clone the repository and open it in a browser; GitHub will not render it inline. It was built from the architecture-diagram skill, which is MIT licensed.
